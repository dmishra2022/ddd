Preface Why This Document Exists

Enterprise code bases decay in predictable ways. A controller gains a quick database call. A domain object sprouts an ORM annotation. A test that used to run in two seconds now needs a database to boot. Six months later nobody can change anything with confidence.

This repository is a reference implementation for a service that resists that decay. It is small enough to read in an afternoon and strict enough that the compiler, the build, and a dedicated test module all refuse to let the usual drift happen.

The patterns applied here, Domain-Driven Design and Hexagonal Architecture, are old enough that most engineers have heard of them and new enough to the current Java 25 and Micronaut 4 stack that it is worth seeing them stitched together in a working, testable project.

Reading this document from top to bottom should leave you with three things:

  1. A clear mental model of what each layer is responsible for and, more importantly, what it is forbidden from doing.
  2. The ability to open any file in the repository and explain why it is there and nowhere else.
  3. Enough confidence to fork this template, replace the Order domain with your own, and have a working service inside a day.

No prior exposure to DDD or hexagonal is assumed. Working familiarity with Java and HTTP services is.

Primer The Big Idea in Three Sentences

If you take away nothing else from this document, take these:

  1. The domain is the center of the universe and knows nothing about the outside world. It is pure Java. It has no idea that an HTTP server, a database, or a framework exist.
  2. The application layer coordinates use cases through narrow interfaces called ports. It defines what it needs ("give me a way to save an order") without caring who provides it.
  3. Everything that talks to the outside world is an adapter, and adapters only ever point inward. A controller depends on a port. A JDBC repository implements a port. Nothing in the middle depends on anything on the edge.

Hexagonal Architecture is the picture. Domain-Driven Design is the vocabulary you use inside the picture. Together they produce code where you can swap PostgreSQL for DynamoDB without touching a single business rule, test a thousand variations of order cancellation in milliseconds, and reason about change by pointing at a module boundary instead of grepping for callers.

Everything else in this document is a careful explanation of those three sentences and how they manifest in the files sitting next to this one.

Part One · I The Problem Without These Patterns

Before we talk about solutions, it is worth being specific about the pain that justifies them. Below is the shape of a typical "layered" service that most engineers have inherited at least once.

A typical layered service, honestly described

Three layers: controller, service, repository. Each layer sees the next one through concrete classes. The domain class is a JPA entity with database annotations and getters and setters. The service class is a thin wrapper that calls one or two repository methods, maybe with a bit of logic sprinkled in. The controller validates input and returns JSON.

In isolation each file looks fine. The problems appear over time:

  • Business rules end up scattered across the service layer, the entity (via lifecycle callbacks or validation annotations), and the controller (for "quick" checks). Nobody can tell you where the rules for cancelling an order actually live.
  • You cannot test the service without a running database or an elaborate ORM mock. Each test takes seconds.
  • Swapping persistence technology is a six-month project because every layer imports jakarta.persistence or your repository implementation directly.
  • Framework upgrades touch every file because the framework reaches into every layer.
  • New engineers learn the service by reading controllers, which show what the API does but hide what the business actually enforces.

Two ways to write the same code

Consider cancelling an order. Here are two versions of the same change: one typical of the layered service above, one from this repository.

Entangled
@RestController
@RequestMapping("/orders")
class OrderController {
    private final OrderJpaRepository repo;
    private final KafkaProducer kafka;

    @PostMapping("/{id}/cancel")
    public OrderEntity cancel(@PathVariable UUID id) {
        OrderEntity o = repo.findById(id)
            .orElseThrow(() -> new ResponseStatusException(NOT_FOUND));
        if (o.getStatus().equals("SHIPPED")) {
            throw new ResponseStatusException(CONFLICT);
        }
        o.setStatus("CANCELLED");
        o.setCancelledAt(Instant.now());
        repo.save(o);
        kafka.send("orders", new CancelMsg(id));
        return o;
    }
}

Business rule, persistence, event publishing, time, and HTTP are all one method. Testing it means spinning up Spring, a database, and a Kafka mock. Replacing Kafka means editing the controller.

Separated
// adapter.inbound.rest
@Controller("/api/v1/orders")
class OrderController {
    private final CancelOrderUseCase cancelOrder;
    // ... other use cases injected ...

    @Post("/{id}/cancel")
    public OrderResponse cancel(@PathVariable String id,
                                 @Valid @Body CancelOrderRequest req) {
        Order o = cancelOrder.cancel(
            new CancelOrderCommand(OrderId.of(id), req.reason()));
        return OrderResponse.from(o);
    }
}

The controller translates HTTP to a command and back. It knows nothing about databases, time, or events. The cancellation rule lives in the aggregate; event publishing lives in the use case; both are tested without any framework at all.

Why this matters The entangled version is easier to write first. The separated version is easier to change for the next five years. Most of software engineering is choosing the second one, deliberately, even when a deadline wants the first.

What we gain

  • Testability. The domain aggregate has nine unit tests that run in a quarter of a second with no framework at all.
  • Readability. Business rules live in one place, named after what the business calls them.
  • Replaceability. Swapping H2 for PostgreSQL is a profile change. Swapping JDBC for DynamoDB is a new adapter class and a wiring change.
  • Resistance to drift. ArchUnit rules fail the build when someone imports a database type into the domain. The structure defends itself.

What we pay

Honesty requires naming the costs:

  • More files. A controller, a request DTO, a response DTO, a command, a use case interface, a service implementation, an aggregate method, a port, a persistence record, a mapper, a Flyway migration. Eleven files to place and later cancel an order.
  • More indirection. You cannot ctrl-click your way from REST to SQL in two hops.
  • Discipline required. If the team does not internalize the rules, the architecture is theatre. The ArchUnit module fights that; the team culture completes it.

The trade is worth it the moment the service outlives its original authors. Most do.

Part Two · II Domain-Driven Design, Used Here

Domain-Driven Design is a long book by Eric Evans. The parts we actually use fit on two pages. This chapter covers them with concrete references to files in the repository.

The one strategic idea: bounded context

A bounded context is a chunk of a business where words mean a specific thing. In the Order Management context, "order" means something precise: a customer intent to purchase, with lines and a status. In a Fulfilment context the same word might mean a packing slip. In Billing it might mean an invoice draft.

The practical consequence: every bounded context gets its own module, its own package root, its own aggregate definition, and does not share domain types with any other context. If Billing needs an order id, it gets a copy of just the id, not the Order class.

"A model is a system of abstractions that describes selected aspects of a domain... There is no such thing as a universal model." Eric Evans, Domain-Driven Design

This entire repository is one bounded context: com.enterprise.starter.order.

The tactical pieces we use

PatternWhat it isExample in this repo
Value Object Immutable, defined entirely by its attributes. Two instances with the same values are the same thing. Money, OrderId, ProductId, OrderLine
Entity Has an identity that persists across changes. Two entities with the same id are the same thing even if their fields differ. Order (an aggregate root is also an entity)
Aggregate A cluster of entities and value objects treated as a single unit for consistency. One root entity controls all access. Order is the root; OrderLine is inside the aggregate.
Domain Event A fact about something that happened. Immutable, past tense, named in the business vocabulary. OrderPlaced, OrderCancelled
Repository The illusion of an in-memory collection of aggregates. Used by application services; implemented by an adapter. OrderRepository port, OrderPersistenceAdapter implementation.
Ubiquitous Language One name per concept, used by code and conversations alike. "Place", "cancel", "line", "status" — all appear verbatim in the code.

Value objects, in code

A value object has three properties: it is immutable, it validates itself on construction, and equality is by value. Java records are a near-perfect fit.

public record Money(BigDecimal amount, Currency currency) {

    public Money {
        Objects.requireNonNull(amount, "amount must not be null");
        Objects.requireNonNull(currency, "currency must not be null");
        amount = amount.setScale(currency.getDefaultFractionDigits(), RoundingMode.HALF_UP);
    }

    public Money add(Money other) {
        requireSameCurrency(other);
        return new Money(this.amount.add(other.amount), currency);
    }
    // ... multiply, isNegative, etc.
}

order-domain/src/main/java/com/enterprise/starter/order/domain/model/Money.java

Notice what is not there: no setters, no mutable state, no framework annotations. Add two Money values in different currencies and you get an exception, not a nonsense result. That is a business rule, enforced by the type system.

The aggregate as consistency boundary

The single most important pattern DDD gives you is the aggregate. An aggregate is a group of objects that must stay internally consistent, with one root through which all changes flow. If a business invariant spans multiple objects, those objects must live inside the same aggregate.

The Order aggregate holds two invariants:

  1. An order must have at least one line.
  2. Every line shares the aggregate's currency, and the total is kept in sync with the lines.

The aggregate enforces these in its factory method:

public static Order place(OrderId id, List<OrderLine> lines, Instant placedAt) {
    Objects.requireNonNull(id, "id must not be null");
    Objects.requireNonNull(lines, "lines must not be null");
    Objects.requireNonNull(placedAt, "placedAt must not be null");
    if (lines.isEmpty()) {
        throw new IllegalArgumentException("An order must contain at least one line");
    }
    List<OrderLine> copy = List.copyOf(lines);
    Money total = computeTotal(copy);
    Order order = new Order(id, new ArrayList<>(copy), total, OrderStatus.PLACED, placedAt);
    order.pendingEvents.add(new OrderPlaced(id, total, placedAt));
    return order;
}

order-domain/src/main/java/com/enterprise/starter/order/domain/model/Order.java

There is no public constructor. The only way to create a placed order is through place(...). The only way to cancel it is through cancel(...). State transitions are explicit and enforced:

public void cancel(String reason, Instant cancelledAt) {
    switch (status) {
        case PLACED -> {
            this.status = OrderStatus.CANCELLED;
            pendingEvents.add(new OrderCancelled(id, reason, cancelledAt));
        }
        case DRAFT, CANCELLED, SHIPPED -> throw new InvalidOrderStateException(
            status, "Order %s cannot be cancelled while in status %s".formatted(id.asString(), status));
    }
}

If a shipped order cannot be cancelled, that rule lives here, in one place, and the compiler ensures no shortcut around it. Not in a service. Not in a validator annotation. Not in a database check. Here.

Domain events

When something significant happens, the aggregate records a domain event. Events are facts about the past: OrderPlaced, not PlaceOrder. They carry only the information a downstream reader needs.

public sealed interface DomainEvent permits OrderPlaced, OrderCancelled {
    Instant occurredAt();
}

public record OrderPlaced(OrderId orderId, Money totalAmount, Instant occurredAt)
        implements DomainEvent { }

public record OrderCancelled(OrderId orderId, String reason, Instant occurredAt)
        implements DomainEvent { }

The aggregate buffers events as they are produced. The use case drains them after a successful save and hands them to a DomainEventPublisher. This gives us two important things: events are only published if the state change actually persists, and the aggregate itself does not depend on any publication mechanism.

The sealed trick Declaring DomainEvent as sealed means every event type in this bounded context is known at compile time. If someone adds OrderShipped next week, every switch on DomainEvent will refuse to compile until it handles the new case. The language itself helps keep the event vocabulary current.

Ubiquitous language in practice

Open Chapter V and read the method names on Order: place, cancel, drainEvents. Open the use cases: PlaceOrder, CancelOrder, GetOrder. These are words the business uses. There is no processOrderDataAsync. There is no handleOrderStateChangeEvent. The vocabulary belongs to the domain expert, not the framework.

Picking the right words is unreasonably hard and worth the effort. Rename a method and the entire call graph tells you about it; rename a concept and the whole team re-aligns on what the system is.

Part Two · III Hexagonal Architecture, Used Here

Hexagonal Architecture was named by Alistair Cockburn in 2005. The hexagon shape is incidental. The idea is: the application has an inside, with business rules, and an outside, with everything else. Code only ever flows inward across the boundary through named interfaces called ports.

This chapter shows the picture, names the layers, and gives the one rule that governs everything.

The picture

Hover any layer in the diagram below. The panel underneath explains what belongs there.

Ports: what the application needs

A port is an interface owned by the application layer that describes a boundary. There are two kinds:

  • Inbound ports describe what the application can do. Something outside calls these. In this repository they are the *UseCase interfaces: PlaceOrderUseCase, GetOrderUseCase, CancelOrderUseCase.
  • Outbound ports describe what the application needs from the outside world. The application calls these. Here they are OrderRepository, DomainEventPublisher, ClockPort.

Both live in the application module. The application owns the definition, which is why the dependency arrow in the figure above only ever flies inward: adapters depend on application-owned types, never the reverse.

// application.port.out: the application declares what it needs
public interface OrderRepository {
    Order save(Order order);
    Optional<Order> findById(OrderId id);
}

// adapter.outbound.persistence: an outbound adapter promises to deliver it
@Singleton
public class OrderPersistenceAdapter implements OrderRepository {
    // JDBC code lives here, hidden behind the interface
}

Adapters: how we meet the world

Adapters are the translators. An inbound adapter translates HTTP, gRPC, Kafka, or a cron trigger into a call to a port. An outbound adapter translates a port call into SQL, HTTP, a message publish, or a system call. The adapter is thick with technology; the port it depends on is thin and clean.

The one rule

The dependency rule Source-code dependencies may only point inward. Inner layers know nothing about outer ones.

From that one rule everything else follows:

  • Domain depends on the JDK. Nothing else.
  • Application depends on domain. Nothing else.
  • Adapters depend on application (through its ports) and domain (for mapping).
  • Adapters do not depend on each other. A REST controller cannot touch a JDBC repository directly; it must go through a port.
  • The composition root (in the bootstrap module) is the only place that knows about every adapter at once, because its only job is to wire them together.

Enforcing that rule by hand is a losing battle. Chapter X shows how a small ArchUnit module makes the compiler keep score.

Why a hexagon and not a circle?

The hexagon is Cockburn's visual way of saying: there is no privileged "top" or "bottom". A controller and a repository are both just adapters. The business logic in the middle treats them symmetrically. A persistence database is not any more special than an HTTP server.

Treat the shape as a mnemonic, not a constraint. The circle version of the same idea is sometimes called "Onion Architecture", and the Clean Architecture diagrams by Robert C. Martin are the same picture again. The vocabulary differs; the dependency rule is identical.

Why the shape matters

Three things to notice:

  1. The REST and persistence adapters never share an edge. There is no arrow between them. A controller cannot import a persistence record because its POM does not declare the dependency and the module system refuses the import.
  2. The application module has one incoming dependency (bootstrap) and no outgoing framework dependencies. It stays pure, which is why its use cases are plain classes with no annotations.
  3. The bootstrap module is the only one with knowledge of everything. This is intentional: wiring is a separate concern from business logic. If you wanted to run the same application layer behind a gRPC adapter instead of REST, you would swap one dependency in bootstrap and change nothing else.

Package layout inside each module

Within a module, packages are organized by responsibility, not by technical layer. The domain module has model, event, exception. The application module has command, port.in, port.out, service. The persistence adapter has entity, repository, mapper, adapter.

Part Three · V The Order Aggregate, Dissected

The Order aggregate is the heart of the system. This chapter walks through its design, its state machine, and the small set of rules it enforces. Every pattern discussed in the DDD chapter is embodied in this one file.

The state machine

An order moves through a small set of named states. Illegal transitions throw InvalidOrderStateException. The state machine is the first thing to internalize.

The rules, listed

  1. An order must have at least one line to be placed. Zero-line orders are rejected at construction.
  2. All lines must share the aggregate's currency. Mixed-currency orders are rejected.
  3. A placed order can be cancelled. A cancelled or shipped order cannot be cancelled again.
  4. Every state transition records a domain event in the aggregate's internal buffer.
  5. Only one entry exists to drain events: drainEvents(), which clears the buffer. The use case drains after a successful save.

Reading the code side by side

The two tabs below show the two things the aggregate does: creation (the factory) and transition (the cancellation).

public static Order place(OrderId id, List<OrderLine> lines, Instant placedAt) {
    Objects.requireNonNull(id, "id must not be null");
    Objects.requireNonNull(lines, "lines must not be null");
    Objects.requireNonNull(placedAt, "placedAt must not be null");
    if (lines.isEmpty()) {
        throw new IllegalArgumentException("An order must contain at least one line");
    }
    List<OrderLine> copy = List.copyOf(lines);
    Money total = computeTotal(copy);
    Order order = new Order(id, new ArrayList<>(copy), total,
                              OrderStatus.PLACED, placedAt);
    order.pendingEvents.add(new OrderPlaced(id, total, placedAt));
    return order;
}

private static Money computeTotal(List<OrderLine> lines) {
    Currency currency = lines.get(0).unitPrice().currency();
    Money total = Money.zero(currency);
    for (OrderLine line : lines) {
        if (!line.unitPrice().currency().equals(currency)) {
            throw new IllegalArgumentException("All order lines must share the same currency");
        }
        total = total.add(line.subtotal());
    }
    return total;
}

The constructor is private. The only way in is place(...). Validation and total calculation happen before the object is observable. Once constructed, the aggregate's invariants hold.

public void cancel(String reason, Instant cancelledAt) {
    Objects.requireNonNull(reason, "reason must not be null");
    Objects.requireNonNull(cancelledAt, "cancelledAt must not be null");
    switch (status) {
        case PLACED -> {
            this.status = OrderStatus.CANCELLED;
            pendingEvents.add(new OrderCancelled(id, reason, cancelledAt));
        }
        case DRAFT, CANCELLED, SHIPPED -> throw new InvalidOrderStateException(
            status,
            "Order %s cannot be cancelled while in status %s".formatted(id.asString(), status));
    }
}

A single switch expression over the enum covers every legal and illegal case. If a future developer adds SHIPPED support, the compiler will force an update here because the switch is exhaustive on a sealed-like enum.

private final List<DomainEvent> pendingEvents = new ArrayList<>();

public List<DomainEvent> drainEvents() {
    List<DomainEvent> drained = List.copyOf(pendingEvents);
    pendingEvents.clear();
    return drained;
}

Events are buffered inside the aggregate. drainEvents is called by the use case after the save completes. If the save fails, the events are never published, which keeps domain state and event stream aligned.

Why the aggregate owns its own state transitions

A common mistake is to put transition logic in the service layer: if (order.getStatus().equals(PLACED)) order.setStatus(CANCELLED);. That gives you an object that is nothing more than a struct and a service that owns the rules. Six months later a different service forgets the check.

Putting the transition on the aggregate makes it impossible to write that broken code: there is no setStatus. You call cancel and the aggregate decides. One method, one rule, one place.

Verification

Nine unit tests on Order cover: empty-line rejection, mixed-currency rejection, successful placement, event emission on placement, cancellation of a placed order, event emission on cancellation, double-cancellation rejection, shipped-order rejection, immutability of the drained events list. All run in under a quarter of a second, no framework involved.

@Test
void cannotCancelAlreadyCancelledOrder() {
    Order order = Order.place(OrderId.generate(), List.of(sampleLine()), NOW);
    order.cancel("customer request", NOW);

    assertThatThrownBy(() -> order.cancel("again", NOW))
        .isInstanceOf(InvalidOrderStateException.class);
}

That is the entire test. No mocks, no containers, no fixtures beyond a sampleLine() helper. The payoff of a pure domain is tests that read like the specification.

Part Three · VI The Ports

A port is an interface that lives inside the application layer and names a boundary. Inbound ports describe what the application can be asked to do. Outbound ports describe what the application needs the world to provide. This chapter lists both, explains the choices behind them, and shows what the use case implementations look like.

Inbound ports: the shape of the application

There is one inbound port per business intention. Not per endpoint. Not per database table. Per intention.

public interface PlaceOrderUseCase {
    Order place(PlaceOrderCommand command);
}

public interface GetOrderUseCase {
    Order get(OrderId id);
}

public interface CancelOrderUseCase {
    Order cancel(CancelOrderCommand command);
}

Three interfaces, one method each. If the system grows a new intention, we add a port; we do not add a method to an existing one. That constraint keeps classes small and dependencies honest: a controller that only needs to place orders takes one port, not a bag of methods it ignores.

Interface segregation This is the I in SOLID applied to the application boundary. A caller declares the slim interface it depends on; the implementation can satisfy many. The REST controller depends on three use case interfaces because it exposes three endpoints.

Commands: input as data

Each inbound port takes a command: an immutable value object that carries exactly the data needed for that intention. Commands live in the application module, not in the REST adapter, because they are part of the application's shape.

public record PlaceOrderCommand(List<OrderLineCommand> lines) {
    public PlaceOrderCommand {
        Objects.requireNonNull(lines, "lines must not be null");
        lines = List.copyOf(lines);
    }
}

public record OrderLineCommand(String productId, int quantity,
                               BigDecimal unitPriceAmount, String currencyCode) { }

public record CancelOrderCommand(OrderId orderId, String reason) {
    public CancelOrderCommand {
        Objects.requireNonNull(orderId, "orderId must not be null");
        Objects.requireNonNull(reason, "reason must not be null");
    }
}

Commands are deliberately simple: strings, numbers, and lists. The use case translates them into domain value objects (OrderLine, Money, ProductId) during execution. This keeps the domain free of parsing concerns and the inbound boundary easy to extend with validation and format negotiation.

Outbound ports: the shape of the world

There are three outbound ports in this template. Each describes a single capability the application needs.

public interface OrderRepository {
    Order save(Order order);
    Optional<Order> findById(OrderId id);
}

public interface DomainEventPublisher {
    void publish(List<DomainEvent> events);
}

public interface ClockPort {
    Instant now();
}

Three decisions worth noting:

  • Repository returns the aggregate type, not a persistence record. The adapter is responsible for mapping to and from storage. The port speaks the domain's language.
  • Event publishing takes a list. This matches how aggregates emit events (one aggregate operation produces one batch) and lets outbound adapters publish atomically where possible.
  • Time is a port. This is the smallest-looking decision with the largest testability payoff. In production the implementation is Clock.systemUTC(); in tests it is a FixedClock that returns the same instant on every call.

Use case services: orchestration without logic

A use case service is where the pieces come together. It accepts a command, calls outbound ports, exercises the aggregate, saves, publishes events, returns the result. It should contain no business rules of its own: those belong on the aggregate.

public class PlaceOrderService implements PlaceOrderUseCase {

    private final OrderRepository orderRepository;
    private final DomainEventPublisher eventPublisher;
    private final ClockPort clock;

    public PlaceOrderService(OrderRepository orderRepository,
                             DomainEventPublisher eventPublisher,
                             ClockPort clock) {
        this.orderRepository = Objects.requireNonNull(orderRepository);
        this.eventPublisher = Objects.requireNonNull(eventPublisher);
        this.clock = Objects.requireNonNull(clock);
    }

    @Override
    public Order place(PlaceOrderCommand command) {
        Objects.requireNonNull(command, "command must not be null");
        List<OrderLine> lines = command.lines().stream()
            .map(this::toOrderLine)
            .toList();
        Order order = Order.place(OrderId.generate(), lines, clock.now());
        Order saved = orderRepository.save(order);
        eventPublisher.publish(saved.drainEvents());
        return saved;
    }

    private OrderLine toOrderLine(OrderLineCommand command) {
        Money unitPrice = new Money(command.unitPriceAmount(),
                                     Currency.getInstance(command.currencyCode()));
        return new OrderLine(ProductId.of(command.productId()), command.quantity(), unitPrice);
    }
}

order-application/src/main/java/com/enterprise/starter/order/application/service/PlaceOrderService.java

A quiet detail There is no @Singleton on PlaceOrderService. The application module declares zero dependency on any dependency-injection framework. Wiring happens in the UseCaseConfiguration factory in the bootstrap module. The service is a plain class that can be instantiated by hand, by Micronaut, by Spring, or by a test, with no changes to its code.

The symmetry

Inbound and outbound ports are drawn with the same arrow in diagrams because they are the same kind of thing: an interface the application owns. The only difference is which side holds the implementation. Inbound: adapter calls into the interface. Outbound: adapter implements it. Both: the application decides the shape.

Part Three · VII The Adapters

Adapters are where the application meets reality. This chapter opens each adapter, shows what it translates, and highlights the small discipline each one maintains.

The REST adapter: translating HTTP to commands

The REST controller does three things and nothing else: it reads the request, maps it to a command, and shapes the result into a response. Business logic is forbidden here.

@Controller("/api/v1/orders")
public class OrderController {

    private final PlaceOrderUseCase placeOrder;
    private final GetOrderUseCase getOrder;
    private final CancelOrderUseCase cancelOrder;

    public OrderController(PlaceOrderUseCase placeOrder,
                           GetOrderUseCase getOrder,
                           CancelOrderUseCase cancelOrder) {
        this.placeOrder = placeOrder;
        this.getOrder = getOrder;
        this.cancelOrder = cancelOrder;
    }

    @Post
    public HttpResponse<OrderResponse> place(@Valid @Body PlaceOrderRequest request) {
        List<OrderLineCommand> lines = request.lines().stream()
            .map(OrderLineRequest::toCommand)
            .toList();
        Order placed = placeOrder.place(new PlaceOrderCommand(lines));
        return HttpResponse.created(OrderResponse.from(placed));
    }

    @Get("/{id}")
    public OrderResponse get(@PathVariable String id) {
        return OrderResponse.from(getOrder.get(OrderId.of(id)));
    }

    @Post("/{id}/cancel")
    public OrderResponse cancel(@PathVariable String id,
                                 @Valid @Body CancelOrderRequest request) {
        return OrderResponse.from(
            cancelOrder.cancel(new CancelOrderCommand(OrderId.of(id), request.reason())));
    }
}

The persistence adapter: translating aggregates to rows

The persistence adapter owns the OrderRecord and OrderLineRecord types, the two JdbcRepository interfaces, and a mapper. The OrderPersistenceAdapter implements the OrderRepository port and does the translation.

@Singleton
public class OrderPersistenceAdapter implements OrderRepository {

    private final OrderJdbcRepository orders;
    private final OrderLineJdbcRepository lines;
    private final OrderEntityMapper mapper;

    @Override
    @Transactional
    public Order save(Order order) {
        OrderRecord record = mapper.toRecord(order);
        OrderRecord saved = orders.existsById(record.id())
            ? orders.update(record)
            : orders.save(record);
        lines.deleteByOrderId(saved.id());
        for (OrderLineRecord line : mapper.toLineRecords(order)) {
            lines.save(line);
        }
        return order;
    }

    @Override
    public Optional<Order> findById(OrderId id) {
        return orders.findById(id.asString())
            .map(record -> mapper.toDomain(record, lines.findByOrderId(record.id())));
    }
}

The mapper is a plain class that walks the record tree and builds domain objects, using a package-visible reconstruction constructor on Order for rehydration. The adapter never leaks a OrderRecord back into the application layer; the port signature forbids it.

Part Four · VIII Lifetime of a Request

The sequence diagram in the previous chapter is a static snapshot. This chapter walks the same flow one step at a time, showing exactly what each component does, what it holds, and what it hands off. Use the arrows below to step through.

Step 1 · HTTP request arrives

A client sends POST /api/v1/orders with a JSON body. Micronaut's Netty-based server, running on a virtual thread, accepts the socket, parses the HTTP envelope, and begins routing.

POST /api/v1/orders HTTP/1.1
Content-Type: application/json

{ "lines": [ { "productId": "SKU-100", "quantity": 2,
               "unitPriceAmount": "19.99", "currencyCode": "USD" } ] }

Step 2 · Micronaut deserializes and validates the request DTO

The request body is bound to PlaceOrderRequest, a record with Jakarta Validation annotations. If validation fails, Micronaut returns 400 before the controller is ever called.

public record PlaceOrderRequest(@NotEmpty @Valid List<OrderLineRequest> lines) { }

public record OrderLineRequest(@NotBlank String productId,
                                 @Positive int quantity,
                                 @NotNull BigDecimal unitPriceAmount,
                                 @NotBlank String currencyCode) {
    OrderLineCommand toCommand() {
        return new OrderLineCommand(productId, quantity, unitPriceAmount, currencyCode);
    }
}

Step 3 · Controller maps the DTO to a command and calls the port

The controller's job is translation: it builds a PlaceOrderCommand and hands it to the inbound port. The controller holds a reference to a PlaceOrderUseCase interface; it does not know (or care) which class implements it.

List<OrderLineCommand> lines = request.lines().stream()
    .map(OrderLineRequest::toCommand)
    .toList();
Order placed = placeOrder.place(new PlaceOrderCommand(lines));

Step 4 · The use case builds domain value objects

Inside PlaceOrderService, the command's primitives are promoted to real domain value objects: Money, ProductId, OrderLine. The service also reads the current time through the ClockPort, keeping itself testable with a fixed clock.

List<OrderLine> lines = command.lines().stream()
    .map(c -> new OrderLine(ProductId.of(c.productId()), c.quantity(),
                           new Money(c.unitPriceAmount(), Currency.getInstance(c.currencyCode()))))
    .toList();
Order order = Order.place(OrderId.generate(), lines, clock.now());

Step 5 · The aggregate enforces its invariants

Inside Order.place(...), the aggregate checks: non-empty lines, consistent currency, non-null arguments. It computes the total, sets its status to PLACED, and buffers an OrderPlaced event. If any check fails, an exception propagates and the save never happens.

Money total = computeTotal(copy);
Order order = new Order(id, new ArrayList<>(copy), total, OrderStatus.PLACED, placedAt);
order.pendingEvents.add(new OrderPlaced(id, total, placedAt));

Step 6 · The persistence adapter writes to the database

The use case calls orderRepository.save(order). The implementation (OrderPersistenceAdapter) opens a transaction, maps the aggregate to records, and writes to the orders and order_lines tables. The entire aggregate boundary becomes the transaction boundary.

@Transactional
public Order save(Order order) {
    OrderRecord record = mapper.toRecord(order);
    orders.save(record);
    for (OrderLineRecord line : mapper.toLineRecords(order)) {
        lines.save(line);
    }
    return order;
}

Step 7 · Events are drained and published

Only after the save returns does the use case drain the aggregate's event buffer and hand the events to the publisher. If the save had failed, no event would have been published, and no downstream consumer would believe the order existed.

Order saved = orderRepository.save(order);
eventPublisher.publish(saved.drainEvents());

Step 8 · The response flows back to the client

The use case returns the saved Order to the controller, which wraps it in an OrderResponse DTO and returns HttpResponse.created(...). Micronaut serializes the response, writes it to the socket, releases the virtual thread, and the request is done.

HTTP/1.1 201 Created
Content-Type: application/json

{ "id": "6c1f...",
  "status": "PLACED",
  "totalAmount": "39.98",
  "currency": "USD",
  "lines": [ ... ],
  "placedAt": "2026-10-11T09:14:03Z" }

What you did not have to think about

Trace the eight steps in your head and notice the absences. The controller never built SQL. The aggregate never asked for the time directly. The use case never looked at an HTTP header. Each class did exactly one job, and the composition of the classes produced the behavior. That is the point of the architecture.

Part Four · IX Virtual Threads

Java 21 shipped virtual threads under Project Loom. Java 25, which this starter uses, treats them as the default way to run blocking code. This chapter explains what they are, why they matter here, and the exact configuration that turns them on.

What virtual threads actually are

A classic Java thread is a thin wrapper around an operating system thread. The OS schedules it, and the JVM pays for the stack. On a typical server you can run perhaps a few thousand of them before context switching and memory pressure degrade the system. That is why "thread per request" fell out of fashion and reactive programming spread.

A virtual thread is scheduled by the JVM, not the OS. Its stack is tiny and growable. You can create millions. When a virtual thread performs a blocking I/O call, it unmounts from its carrier platform thread, and the carrier moves on to run another virtual thread. The syscall sleeps, the carrier does not.

The practical outcome: imperative, blocking code (repository.save(order)) uses the CPU as efficiently as a reactive pipeline, without the cognitive overhead of callbacks, operators, or Mono and Flux types infecting your signatures.

Terminology A carrier thread is a platform (OS) thread owned by the JVM scheduler. A virtual thread runs on top of a carrier when it needs the CPU, and unmounts when it blocks. The JVM maintains a small pool of carriers, roughly equal to the number of CPU cores.

Where they are enabled here

Two executors are flipped to virtual in application.yml. One handles Micronaut's event loop blocking offload; the other handles anything the application explicitly dispatches to the blocking executor.

micronaut:
  application:
    name: order-service
  executors:
    io:
      virtual: true
    blocking:
      virtual: true

order-bootstrap/src/main/resources/application.yml

These two toggles replace the fixed-size pools that would otherwise back those executors with virtual-thread executors. The HTTP server, the JDBC repository calls, and any @ExecuteOn(TaskExecutors.BLOCKING) code paths all run on virtual threads.

What this changes in the code

Almost nothing. That is the entire point. The PlaceOrderService looks exactly like it would in a Java 8 service: a method that calls other methods. The virtual thread model lets you keep writing that way without paying the historical price.

public Order place(PlaceOrderCommand command) {
    List<OrderLine> lines = command.lines().stream().map(this::toOrderLine).toList();
    Order order = Order.place(OrderId.generate(), lines, clock.now());
    Order saved = orderRepository.save(order);          // blocks; virtual thread unmounts
    eventPublisher.publish(saved.drainEvents());        // may also block
    return saved;
}

No CompletableFuture. No Mono. No flatMap. The code reads top to bottom and executes the same way. During the two blocking calls, the carrier thread is released to serve another request.

Rules of thumb that still apply

  • Virtual threads are cheap, not free. They are perfect for I/O-bound work. CPU-bound work still needs a bounded pool so that one request cannot consume the server.
  • Thread locals leak. Avoid storing per-request state in ThreadLocal. Prefer ScopedValue (preview in recent JDKs) or explicit parameters.
  • Synchronized blocks pin. A virtual thread that enters a synchronized section cannot unmount. Prefer ReentrantLock, or keep critical sections short.
  • JDBC drivers vary. Modern drivers (HikariCP, pg-jdbc, h2) work well with virtual threads; some older ones pin on native sections. Measure before celebrating.

Why this fits a hexagonal architecture

Hexagonal and virtual threads reinforce each other. Hexagonal says: write synchronous, framework-free business code. Virtual threads say: synchronous code scales. The combination gives you an application layer that reads like a specification and performs like a reactive stack, with none of the ceremony of the latter.

Part Four · X Enforcing Architecture with ArchUnit

An architecture that is only enforced by code review decays. The architecture-tests module turns the rules of this project into executable tests that run on every mvn verify. Breaking a rule fails the build.

The idea

ArchUnit is a Java testing library that lets you write assertions over a set of imported classes. "No class in the domain package may depend on a class whose name starts with io.micronaut." "Every class in the application service package must be in a package named service." These are tests in the same JUnit sense as any other, and they appear in the same surefire report.

The four rule files

Rule classWhat it enforces
HexagonalArchitectureTestThe onion rule: adapters depend on application, application depends on domain, domain depends on nothing else. Encoded as ArchUnit's onionArchitecture() DSL.
DomainPurityTestFour rules on the domain package: no Micronaut, Netty, or Reactive types; no Jakarta or Javax framework types; no JDBC, Flyway, or SQL types; no application or adapter imports.
ApplicationLayerTestNo adapter dependencies, no framework dependencies (beyond the few allowed), naming conventions on use cases and services.
AdapterIsolationTestInbound adapters cannot import outbound adapters, and vice versa. Controllers live in the controller package, repositories in the repository package.

Reading a rule

The onion rule reads almost like English:

onionArchitecture()
    .domainModels(DOMAIN + "..")
    .applicationServices(APPLICATION + "..")
    .adapter("rest", ADAPTER_REST + "..")
    .adapter("persistence", ADAPTER_PERSISTENCE + "..")
    .adapter("time", BOOTSTRAP + ".adapter.time..")
    .adapter("eventing", BOOTSTRAP + ".adapter.eventing..")
    .adapter("bootstrap", BOOTSTRAP + "..")
    .check(ALL_CLASSES);

If a controller imports an entity from the persistence package, this rule fails with a clear message naming the offending class and the forbidden import. No warning. No code review. Build fails.

Keeping generated classes out of the picture

Micronaut's annotation processor generates synthetic classes ($Order$Introspection, $OrderController$Definition) that would otherwise fail the onion rule for perfectly good reasons. A tiny ImportOption filters them out:

public class DoNotIncludeGeneratedClasses implements ImportOption {
    @Override
    public boolean includes(Location location) {
        String uri = location.asURI().toString();
        return !uri.contains("/$") && !uri.contains("$$");
    }
}

The meta-test

How do we know the rules are not vacuously passing? There is a fixture package of deliberately broken classes and a meta-test that feeds just those classes into each rule, asserting the rules reject them.

@Test
void domainPurityRejectsFrameworkImports() {
    JavaClasses onlyFixtures = new ClassFileImporter()
        .importPackages("com.enterprise.starter.architecture.violationfixture");

    assertThatThrownBy(() -> DomainPurityTest.NO_FRAMEWORK.check(onlyFixtures))
        .isInstanceOf(AssertionError.class);
}

If someone accidentally weakens a rule such that it no longer catches a known violation, the meta-test fails. The rules check the code, and the meta-test checks the rules.

Why this changes behavior over months

A rule that fails the build teaches faster than a lint warning or a review comment. A new engineer who writes a shortcut sees the build go red before they open a pull request. By the second or third encounter, the rule is internalized. The architecture becomes a habit instead of a document.

Part Five · XI Exercises

Reading is passive. Working the code is how the patterns settle. Below are ten exercises in increasing difficulty. Each one is phrased as a change to the repository with a clear end state. Attempt them in order.

Exercise 1 · Add a ship transition to the Order aggregate

Add a ship(Instant shippedAt) method on Order that transitions a PLACED order to SHIPPED and records an OrderShipped event. Add unit tests covering: successful shipment, double-ship rejection, cancellation-after-ship rejection.

Done when: mvn -pl order-domain test passes with your new tests, and the existing cancel behavior rejects a shipped order.

Exercise 2 · Expose the ship transition over HTTP

Add a ShipOrderUseCase inbound port, implement it in a ShipOrderService, add a wiring entry in UseCaseConfiguration, and expose POST /api/v1/orders/{id}/ship. Return 409 Conflict for invalid state via the existing exception handler.

Done when: an integration test POSTs to the ship endpoint and asserts the resulting OrderResponse has status SHIPPED.

Exercise 3 · Replace LoggingDomainEventPublisher with an in-memory recorder

Create a second DomainEventPublisher implementation that stores events in a CopyOnWriteArrayList, selectable by a Micronaut condition on an environment. Use it in integration tests to assert exact event sequences.

Done when: an integration test places an order, drains the recorder, and asserts a single OrderPlaced event with the correct total.

Exercise 4 · Add a cancellation reason catalogue

Introduce a CancellationReason enum in the domain with values CUSTOMER_REQUEST, PAYMENT_FAILURE, FRAUD. Change cancel to take the enum. Update the command, request DTO, and tests. Keep the architecture tests green.

Done when: the request body for cancel accepts a reason code string and the domain refuses unknown values at the DTO boundary.

Exercise 5 · Enforce "no setters on domain entities"

Add a new rule in DomainPurityTest that fails if any public method on a domain class is named set*. Confirm it catches a deliberately added setter (then remove the setter). This is one line of ArchUnit and a thirty-second feedback loop.

Exercise 6 · Pagination on list orders

Add a findAll(int offset, int limit) method to OrderRepository, a ListOrdersUseCase, and GET /api/v1/orders?offset=&limit=. Validate limits, cap them, and return a response envelope with pagination metadata.

Exercise 7 · Replace H2 with PostgreSQL in dev

Use Docker Compose to run PostgreSQL locally. Update application-dev.yml to point at it. Confirm the Flyway migration runs clean. Confirm all integration tests pass against both H2 (CI) and PostgreSQL (dev) without code changes.

Payoff: you have now proven the persistence port's abstraction holds across engines.

Exercise 8 · Swap the REST adapter for gRPC

Create a new module order-adapter-grpc. Add a proto file for the three operations. Implement a service class that depends on the same inbound ports. Wire it in bootstrap behind a profile. Do not touch application or domain code.

Payoff: you now have two inbound adapters serving the same application layer. This is the hexagonal promise, tested.

Exercise 9 · Introduce a second bounded context

Fork order-domain, order-application, and so on into a fulfilment-* set of modules. Give it a Shipment aggregate with its own state machine. Add an OrderShippedListener in the fulfilment context that reacts to OrderShipped. Keep the two contexts' domain packages non-overlapping.

Exercise 10 · Outbox-based event publication

Replace the current publisher with an outbox implementation: inside the same transaction as the aggregate save, insert the events into an order_outbox table. A separate scheduled process reads unpublished rows, delivers them to Kafka, and marks them published. Prove transactional consistency with a test that fails the Kafka call and asserts no gap.

Payoff: you now understand why the aggregate buffers events and why the use case drains them after save and not during.

Part Five · XII Glossary

A short, opinionated dictionary. Each entry is phrased the way it is used in this repository, which is not always how the original texts define it.

Adapter
A class that translates between the outside world and an application port. Inbound adapters call a port; outbound adapters implement a port.
Aggregate
A cluster of domain objects treated as a single unit for consistency. One entity in the cluster is the root; all mutations flow through it.
Application layer
The module containing use case interfaces, their implementations, and the inbound and outbound ports. Orchestrates the domain. Contains no business rules of its own.
ArchUnit
A Java library for writing architecture rules as JUnit tests. Used in this repo to enforce the dependency rule, naming conventions, and layer isolation.
Bounded context
A region of a business where words have one agreed meaning. Usually one deployable service and one module tree. This project is one bounded context: Order Management.
Command
An immutable value that carries the input for one use case. Lives in the application layer, between the inbound adapter and the use case.
Composition root
The one place in the application where concrete classes are wired together into an object graph. Here, the order-bootstrap module.
Dependency rule
Source-code dependencies may only point inward. The single rule that governs hexagonal, onion, and clean architectures.
Domain
The subject of the software. For this project, the domain is placing and cancelling orders. Everything else is machinery to serve it.
Domain event
A past-tense fact emitted by an aggregate when something significant happens. Immutable. Named in the business's language.
Entity
A domain object with an identity that persists across state changes. Not interchangeable with another instance that happens to have the same fields.
Hexagonal architecture
Alistair Cockburn's name for the ports-and-adapters pattern. The hexagon shape is incidental; the dependency rule is the point.
Inbound port
An interface the application exposes to the outside world. Called by inbound adapters. Here: the *UseCase interfaces.
Onion architecture
Jeffrey Palermo's circular drawing of the same dependency rule. ArchUnit's DSL calls the pattern onionArchitecture().
Outbound port
An interface the application declares to describe what it needs from the outside world. Implemented by outbound adapters. Here: OrderRepository, DomainEventPublisher, ClockPort.
Port
Any interface the application owns to define a boundary. Both inbound and outbound ports are ports.
Repository
An abstraction that behaves like an in-memory collection of aggregates. The application uses one; an adapter implements it against a real datastore.
Ubiquitous language
A shared vocabulary between developers and domain experts, reflected directly in the code. If the business says "place an order", so does the method.
Use case
One business intention, modelled as an interface in the application layer. A PlaceOrderService implements PlaceOrderUseCase.
Value object
An immutable object defined by its attributes. Two instances with equal attributes are the same object. Java records fit perfectly.
Virtual thread
A JVM-scheduled thread with a tiny, growable stack. Project Loom's answer to the thread-per-request versus reactive dilemma. Default in Java 21+.
